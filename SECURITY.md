# Security policy

FPL Andres proxies a third-party API, holds a production Postgres database and
sends email on a subscriber's behalf. That is enough attack surface to warrant a
stated disclosure route rather than an assumed one.

## Reporting a vulnerability

Open a [private security advisory](https://github.com/JamieMBright/fpl-andres/security/advisories/new)
on this repository. That channel is not public and does not require the reporter
to have write access.

Please do **not** open a public issue for anything that could be exploited
before it is fixed.

Include whatever you have: the route or file, the conditions needed to trigger
it, and what an attacker gets. A proof of concept helps but is not required to
report.

## What to expect

| Stage              | Target                                               |
| ------------------ | ---------------------------------------------------- |
| Acknowledgement    | 3 working days                                       |
| Initial assessment | 10 working days                                      |
| Fix or mitigation  | Depends on severity; you will be told which and when |
| Public disclosure  | After a fix ships, and credited unless you decline   |

This is a personal project maintained by one person. The targets above are
honest intentions rather than a contractual SLA, and if a deadline slips you
will be told rather than left waiting.

## Scope

In scope:

- The serverless functions under `api/` — `/api/health`, `/api/fpl/*` and
  `/api/team/:id`. These are unauthenticated proxies to the public FPL API.
- The web application under `apps/web/`.
- The Python package under `python/fpl_andres/`, including credential handling
  and anything written to Supabase.
- The database schema and row-level security posture under `supabase/`.
- CI workflows and anything that could lead to a supply-chain compromise.

Out of scope:

- Vulnerabilities in the Fantasy Premier League API itself. Report those to the
  Premier League, not here.
- Denial of service demonstrated by simply sending a lot of traffic. Rate
  limiting on the public proxies is a known gap and is tracked in
  `IMPROVEMENTS.md` as item 72; a report that it is missing is welcome, a
  demonstration that hammers the endpoint is not.
- Findings that require a compromised developer machine or a stolen deployment
  secret to reproduce.
- Reports generated by a scanner with no evidence of exploitability.

## What this project already does

Stated so a reporter can tell a design decision from an oversight:

- **No user accounts, no sessions, no passwords.** A Team ID is a public
  identifier and is treated as one.
- **Every database table is `force row level security` with no policy.** Nothing
  is readable by the browser. All writes go through the service role from
  server-side jobs. See [`docs/adr/0001-forced-rls-with-no-policies.md`](docs/adr/0001-forced-rls-with-no-policies.md).
- **The service-role key is never returned, logged or put in an exception.**
  Upstream error bodies are scrubbed of it before they reach a message, and a
  regression test asserts the property rather than trusting the masked `repr`.
- **Handler failures return an opaque request id**, not the exception text. The
  detail goes to the server log under the same id.
- **The FPL proxy is allow-listed by path**, not open. An unrecognised path is
  refused before any upstream request is made.
- **Caller-supplied workflow metadata is redacted** by name and by shape before
  it is persisted, so a credential pasted into a parameter is not stored.
